# dsh-keep-going

[English](README.md) | 中文

**重启 DSH，但不打断正在进行的活儿。**

## 痛点

你手上同时开着好几个对话，都在正常干活。其中一个对话要求重启 DSH——比如刚装了个插件要生效，或者改了个设置。DSH 停了，几秒后回来了，可**其它所有对话也一起停了**：正在写的回答被打断在半句话上，跑着的长任务不再继续，而且没有任何东西告诉它们发生过什么。什么都没坏，只是一切都在等人——等你去每个对话里挨个说一句"继续"。

`dsh-keep-going` 就是为了不再发生这种事。一个对话的重启，只该是它自己的事：

- **正在写的回答会先写完**，而不是被砍断；
- **确实被打断的对话，之后会被唤醒并被告知接着干**——发起重启的那个收到它自己的提示，其它几个收到一句中立的"请继续"；
- **还在进行的长任务目标会自动重新开启**，不需要谁来催。

## 它怎么做

1. **它会等。** 当有人要求重启或关闭时，DSH 不会立刻停。插件先等到正在回答的轮次结束，然后请 DSH 按正常流程自己收尾退出。
2. **它会接上。** 退出之前，它记下是哪个会话要求重启的。DSH 再次启动后，插件等这个会话回来，给它发一条"接着干"的消息——你不需要再说任何话。
3. **它把长任务的目标接回来。** DSH 在会话每次启动时都会解除目标，所以重启前正在跑的目标，重启后会一直闲着，直到有人再说一句。这个插件会把仍然处于 `active` 的目标重新武装起来——这批正是被重启打断的；之前主动暂停、标记受阻或已完成的目标一律不动。

```
你或助手要求重启
        │
        ▼
等到正在回答的轮次结束
        │
        ▼
记下要唤醒的会话，然后让 DSH 按正常流程收尾退出
        │
        ▼
服务管理器（systemd、Windows 服务……）重新启动 DSH
        │
        ▼
DSH 启动 → 唤醒被打断的会话 → 工作继续
```

## 它不负责什么

| 这里不管的事 | 由谁负责 |
| --- | --- |
| DSH 退出后把它重新启动 | 你的服务管理器——比如 systemd 的 `Restart=always` |
| 把导致 DSH 起不来的插件装回原样 | 你自己；DSH 会报错并退出，不会自我修复 |
| 设置页、浏览器里的按钮、进程面板 | 都没有——这个插件不参与网页界面 |
| 唤醒"你要求重启时本来就空闲"的会话 | 有意为之：它们没有需要接着做的事 |

把范围压到这么小是刻意的。名字只说一件事：重启之后，接着干。

## 安装

```sh
# 从 GitHub
dsh plugin --profile web add git+https://github.com/Carrick-K7/dsh-keep-going.git

# 从本地目录
dsh plugin --profile web add /path/to/dsh-keep-going
```

然后重启一次 DSH，让插件被加载。

**一个前提**：DSH 退出后必须有东西把它重新启动。没有的话，重启就等于把 DSH 停掉了。见[部署](#部署)。

## 工具与命令

| 你用的东西 | 它做什么 | 会话会自动继续吗 |
| --- | --- | --- |
| `restart_harness`（助手用） | 等当前回答结束后重启 | 会 |
| `shutdown_harness`（助手用） | 关闭 DSH，不重启 | 不适用 |
| `cancel_harness_action`（助手用） | 取消还没执行的重启或关闭 | 不适用 |
| `/restart`（你输入） | 等当前回答结束后重启 | 不会，它等你 |
| `/shutdown`（你输入） | 关闭 DSH，不重启 | 不适用 |

`restart_harness` 的参数：

| 参数 | 含义 |
| --- | --- |
| `continuePrompt` | 会话被唤醒时收到的内容。会替换设置里的默认文字。 |
| `waitMs` | 这一次重启愿意等多久（毫秒）。会替换 `drainTimeoutMs`。 |
| `force` | 即使**别的**会话正在回答，也照样重启（默认否）。不带它时请求会被拒绝，并列出正忙的会话——这样一个会话永远没法悄悄掐掉别人的工作。 |

## 唤醒哪些会话，各自收到什么

凡是回答被这次重启打断的会话，都会被唤醒，不让任何一个悬在半空：

- 提出重启的会话收到**它自己的**指令（它的 `continuePrompt`，或设置里的默认文字）；
- 其它被打断的会话收到一条中立的"请继续"通知，里面不包含任何具体任务，由它自己判断刚才在做什么；
- 本来就空闲的会话不会被唤醒——它们没有需要接着做的事。

这个区分很关键：把发起者的指令塞给别的会话，正是之前"一个会话跑去干另一个会话的活"的原因。

## 设置

这些值写在 `settings.yaml` 的 `dsh-keep-going` 段里，也可以在设置页里改：

```yaml
dsh-keep-going:
  continuePrompt: DSH 已重启完成，请继续未完成的工作。
  drainTimeoutMs: 600000   # 10 分钟：不再等，直接收尾退出
  stuckAgentMs: 60000      # 60 秒没有活动：不再把它当成正在回答
  stormLimit: 5            # 下面这个时间窗内重启超过 5 次：只重启，不唤醒
  stormWindowMs: 300000
```

两个值得知道的行为：

- **安静下来的轮次不再挡路，完全不了解的轮次仍然算数。** 一个显示为"正在运行"、但 `stuckAgentMs` 时间内没有任何活动的会话，不再拖住重启；而**完全没有活动记录**的会话仍然算正在运行——所以重启绝不会因为"插件还没见过这个会话"就丢掉一段回答。
- **等待上限是强制执行，不是取消。** `drainTimeoutMs` 到了，DSH 照样退出，而且"请继续"的那张便条已经写好。你要求过的重启不会被悄悄丢掉。

## 它写的文件

全部在 `$DSH_HOME/dsh-keep-going/` 里：

- `restart.json` — DSH 退出前写下，下次启动时读取并删除。
- `state.json` — 最近几次重启的时间，用来防止反复重启。

想取消一次还没执行的唤醒，把这个目录删掉即可。

## 部署

**Linux + systemd。** 一个能在退出后重新启动 DSH 的服务就够了：

```ini
[Service]
ExecStart=/path/to/dsh web --host 127.0.0.1 --port 3080
Restart=always
RestartSec=3
```

因为插件是请 DSH 自己收尾退出、而不是把它杀掉，所以数据会写完、端口会释放，进程才结束。之后服务管理器启动一个新的 DSH，它读那张便条并唤醒会话。

**Windows，或者没有服务管理器。** 需要一个能在 DSH 退出后把它启动起来的东西——Windows 服务、计划任务，或者一个常驻在通知区域的小启动器。插件自己从不启动进程。

## 目标

**只要目标还是运行中（`active`），它就一直在跑。** 规则就这一条：`active` 意味着继续，重启、关掉窗口、闲置一下午都不改变它。每一次启动都会把它重新武装——不管这次重启是某个对话要求的、你手打的，还是服务管理器做的；也不管事后有没有会话被唤醒。

只有三件事会让它停，而这三件**都不是这个插件干的**：

| 停下来的原因 | 由谁做 |
| --- | --- |
| 你把它暂停了 | 你，或助手按你的指示 |
| 它做完了 | 助手把目标标记为完成 |
| 它没法继续了 | DSH 自己：回合数用尽，或某一轮连排队都排不上（没额度、凭据无效等） |

这样停下来的目标会一直停着——本插件**不会**把它弄回来，所以"我是故意暂停的"永远优先。如果停下来的原因只是临时的（比如额度），等处理好之后，让它恢复即可。

目标和会话是**各自独立**恢复的：没有任何会话被唤醒时，目标照样跨重启继续跑；反过来，被唤醒的会话也未必牵涉任何目标。

## 兼容性

针对 DSH `0.1.5-rc.2` 编写并测试。插件声明了它用到 DSH 的哪些部分，所以在差异很大的 DSH 版本上安装会提示不匹配，而不是启动时悄无声息地失败。

## 给开发者

```sh
node --test "test/*.test.js"   # 26 个测试
```

- `lib/policy.js` — 所有判断（什么时候停止等待、哪些轮次算卡住、什么时候停止唤醒、唤醒谁）都在这里，都是没有副作用的小函数。
- `lib/state.js` — 读写上面那两个文件。
- `lib/index.js` — 把这两部分接到 DSH 上，并在会话启动时把被打断的目标接回来。
- `test/smoke.test.js` — 用一个替代 DSH 的假上下文启动插件，其中有一个测试会跑完整的"重启并唤醒"流程。
